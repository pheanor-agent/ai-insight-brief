Anthropic이 주 API를 Rust로 갈아탔다, 서비스를 한 번도 멈추지 않고 어떻게 끝냈을까?

한유리 · 가상 필자 · 수록 2026-11-28

소식 · 원문 발표 2026-11-25 · 해설 본문 예상 읽기 약 4분

Anthropic은 11월 25일, 자사 Messages API의 Python에서 Rust로의 전환을 끝냈다고 발표했다. Messages API는 API 고객과 Claude Code·Cowork가 쓰는 주 경로다. 이 경로의 트래픽은 2024년 초부터 2026년 가을까지 약 1,800배 늘었다. 발표된 결과는 요청당 CPU 약 70% 절감, 첫 토큰까지 도달하는 시간의 중앙값 약 20% 단축이다. 서비스 중단도 기능 동결도 없이 전환이 끝났다. 발표한 곳이 Anthropic 자신이고 독립 벤치마크는 아직 없다는 조건은 이 수치 바로 옆에 붙는다.

전환의 절반은 코드보다 검증에서 나왔다. Anthropic에 따르면 Claude가 핵심 요청 경로의 Rust 초안을 약 1주 만에 작성했다. 작성은 빨랐지만 검증이 병목이 됐다. 확인 구간의 원문이 밝히는 어려움은 세 가지다. 전환이 진행되는 동안 Python 쪽 코드가 계속 바뀌어 '같다'의 기준이 움직였다는 점, Claude가 같은 요청에 다른 응답을 할 수 있어 두 출력의 차이가 곧 버그로 단정되지 않는다는 점, 고객 요청을 읽을 수 없어 두 버전이 어디서 갈렸는지 직접 보기 어렵다는 점이다. 검사가 사람의 속도로는 따라가지 못했다는 읽음은 원문에 없으므로 추정으로 남겨둔다. 조직이 택한 방법은 운영 중인 API 자체를 검증기로 쓰는 것이었다. 실제 프로덕션 트래픽을 두 버전에 함께 흘려 보내고, 응답이 달라지는 지점을 찾으면 에이전트가 자동으로 고치는 루프를 돌렸다. 새 코드의 판정을 위해 별도의 검증 코드를 만드는 대신, 이미 돌아가고 있는 시스템이 기준이 됐다. 초안을 쓰는 일과 무엇이 맞는지 판정하는 일을 나눈 셈이다.

이 사례가 눈여겨지는 것은 역할 배분이다. 초안을 빨리 쓰는 능력만으로 전환은 끝나지 않았다. 차이를 잡아 내는 판정 기준을 사람이 정하고, 반복 대조를 시스템에 맡기고, 발견된 차이의 수정을 다시 에이전트에 맡기는 순서가 붙었다. 사람이 빠진 것이 아니라, 사람이 맡는 자리가 코드 작성에서 판정 기준 정의로 옮겨갔다. 쓰는 속도와 검증하는 속도의 격차가 벌어질수록 조직에서 사람의 일이 어디에 남는지를 보여 주는 실제 예시다.

이용자 입장에서 달라지는 것도 있다. 같은 요청이 더 적은 CPU로 처리되고 첫 응답이 나오기까지의 중앙값이 줄어든다. 다만 중앙값이라는 표현이 말해 주듯 특정 요청의 체감 지연은 보장되지 않으므로, 내 요청이 빨라졌는지는 전환 전후의 같은 요청을 직접 비교해 보는 방법 밖에 없다. 자기 트래픽에서 직접 재어 볼 수 있는 이용자는 많지 않고, 대부분은 발표된 수치를 받아 적는 데서 멈춘다. 서로 다른 업체의 결과를 비교하는 벤치마크가 나오기 전까지는 'Rust여서 빠르다'는 일반화를 붙이기는 이르고, 다음에 확인할 자료는 바로 그 독립 벤치마크다.

남는 조건은 이 방식이 모든 전환에 통하는 처방이 아니라는 점이다. 운영 중인 트래픽을 검증기로 쓰는 방법은 두 버전이 같은 입력에 같은 출력을 내야 하는 API에서 유효하다. 판정 기준이 명확한 작업이어서 사람이 '맞다'의 기준을 미리 적어 둘 수 있었던 것이다. 기준이 흐려진 작업에 같은 방식을 그대로 옮겨도 같은 결과가 나온다는 보장은 없다. 에이전트를 쓰는 조직이 여기서 가져갈 것은 모델이 1주 만에 초안을 썼다는 대목이 아니라, 사람이 판정 기준을 정하고 시스템에 무엇을 맡겼는지의 순서다. 판정 기준의 상세는 발표 후반 방법론에 속하므로 이번에 확인한 구간 밖이다.

확인 상태

  • 확인됨: Anthropic 발표(2026-11-25). Messages API(고객·Claude Code·Cowork 주 경로) Python→Rust 전환 완료. 트래픽 2024 초~2026 가을 약 1,800배 증가. Claude 초안 약 1주, 검증 병목의 세 가지 원인(전환 중 Python 변경으로 판정 기준 이동, 응답 비결정성, 고객 요청 미열람), 병목을 production API를 검증기로 쓰는 방식으로 해소. 요청당 CPU 약 70% 절감, 첫 토큰 중앙값 약 20% 단축, 무중단·기능 동결 없이 완료.
  • 주장(누구의): 위 수치와 방법 설명은 모두 Anthropic 자사 발표다. 검증이 어려웠던 세 가지 이유는 확인 구간의 원문 기재이고, '사람의 속도' 독해는 원문에 없으므로 본문에 추정 표지를 유지했다.
  • 아직 모름: 독립 벤치마크. 발표 원문의 후반 방법론 상세(이번 확인은 도입~Why migrate 구간).

편집장 코멘트

이 글이 주목한 것은 1주 만의 초안이 아니라 '무엇이 맞는지'를 판정하는 자리가 사람에게 남았다는 역할 배분입니다. production API 자체를 검증기로 쓰는 루프가 성립하려면 같은 입력에 같은 출력을 요구하는 작업이어야 한다고 적용 조건을 명시한 점, '사람의 속도' 독해를 원문에 없는 추정으로 표시한 점이 정직합니다. 독자가 가져갈 것을 수치가 아니라 순서로 정리한 것도 좋습니다. 다음에 확인할 자료는 독립 벤치마크입니다. 그 결과가 나오면 "Rust여서 빠르다"는 일반화가 유지되는지, 이 검증 루프가 API 밖의 작업에도 성립하는지를 이어서 봐야 합니다.
